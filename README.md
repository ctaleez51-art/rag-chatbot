# 종합소득세 인적공제 상담 챗봇

2025년 귀속 세법 기준. 설계는 [PRD.md](PRD.md).

## 서비스 소개

종합소득세 신고 대상자가 "우리 부모님도 기본공제 되나요?" 같은 인적공제 질문을 하면, 국세상담센터 Q&A와 키워드 연말정산 자료에서 근거를 찾아 자료 번호([QA-006] 같은)를 붙여 답한다. 답 아래 출처를 누르면 그 자료의 원문이 보인다. 모두 사용자 컴퓨터 안에서 돈다(검색은 브라우저, 답은 Ollama).

## 설계 결정 요약

자세한 것은 [PRD.md](PRD.md).

- 범위: 인적공제(배우자·부양가족 기본공제, 경로우대·장애인·부녀자·한부모 추가공제), 2025년 귀속만. 공제로 줄어드는 세금 계산은 하지 않는다.
- 자료: 국세상담센터 자주묻는 Q&A 인적공제 107개(QA-001부터 QA-107까지), 키워드 연말정산 인적공제(KW-001부터 KW-080까지). 공개해도 되는 자료만 쓴다. 자료 안에서 서로 다른 8곳은 고쳐서 쓴다.
- 찾는 방법: 뜻 검색(embeddinggemma-300m, 768차원) 10개 + 낱말 검색(BM25) 5개 = 15개. 모두콘 참조 구현의 조각 형식(id·text·url·section·vector)과 검색·프롬프트 흐름을 그대로 쓰고, 조각만 내 자료로 바꿨다.
- 출처가 필요한 조건: 자료 안 질문에 답할 때는 그 내용이 실제로 적힌 조각의 번호를 붙인다(실험 1에서 채택).
- 자료 밖 질문: "제가 가진 자료에는 없습니다"라고 답하고 번호를 붙이지 않는다. 찾은 자료가 질문과 많이 다르면(뜻 비슷함 55% 미만) 짧게 답하고 모르는 부분은 없다고 한다.
- 답 모델: qwen3.5:2b (Ollama).
- 배포: 하지 않는다. 제출은 이 저장소 주소로 한다.
- 자료 갱신 책임: 저장소 주인이 매년 귀속 연도가 바뀔 때 자료를 새로 받아 조각을 다시 만든다.

## 사용 조건

1. Node.js 설치: nodejs.org에서 LTS 버전을 받아 설치한다.
2. Ollama 설치·실행: ollama.com에서 받아 설치하고 실행한다.
3. 답 모델 받기: 터미널(Windows는 PowerShell)에서  
   `ollama pull qwen3.5:2b`
4. 저장소 받기: 터미널(Windows는 PowerShell)에서  
   `git clone https://github.com/ctaleez51-art/rag-chatbot.git`  
   `cd rag-chatbot`
6. 설치 후 켜기:  
   `npm.cmd install`  
   `npm.cmd run dev`
8. 브라우저에서 http://localhost:5173 접속. 처음 한 번 뜻 검색용 모델(약 200MB)을 내려받는다.


## 출처 표시

- 답 아래 출처를 누르면 그 조각의 원문이 앱 안에 보인다.
- 국세상담센터 Q&A 조각(QA-001부터 QA-107까지)의 "원문 보기" 링크는 모두 같은 페이지(<https://call.nts.go.kr/call/qna/selectQnaInfo.do?mi=1318>)로 간다. 이 사이트는 질문마다 따로 주소를 주지 않고, 한 페이지에서 질문을 누르면 내용을 불러오는 방식이기 때문이다.
- 키워드 연말정산 조각(KW-001부터 KW-080까지)은 웹 주소가 없는 문서(2025년 귀속 키워드연말정산게시용.hwp)에서 옮긴 것이라, 그 내용을 옮긴 [source/키워드연말정산-인적공제.md](source/키워드연말정산-인적공제.md)를 이 저장소에 올리고 그 주소로 연결한다.

관찰한 근거

- ②, ③ 모두 맞는 자료를 1등으로 찾았는데, 답을 만드는 모델(qwen3.5:2b)이 틀린 말을 넣었다. ②는 자료의 출생연도(1955년)를 2025년으로 바꿨고, ③은 관계없는 조각(QA-107)을 첫 근거로 댔다.
- ③은 "[자료에 대한 근거 조각]:" 같은 꼬리표를 지어내 붙이고, 자료 문장을 그대로 옮기지 않고 바꿔 말했다. 지금 프롬프트에는 답의 모양(그대로 옮기기, 길이)에 대한 지시가 없다.
- ⑤는 자료의 "초과하면 받을 수 없다" 문장을 그대로 옮겨 놓고도 600만원을 "가능"이라고 했다. 2B 모델이 금액 크기 비교를 틀렸다.
- ⑥은 답이 맞았지만(기준 1 맞음), 맞는 자료 QA-071이 3등이라 기준 2에서 ❌이다. 답도 "소득·연령요건 충족시"라고만 해서 자료에 있는 구체적인 요건(70세 이상, 연간소득금액 100만원 이하)을 빼고 너무 단순하게 답했다(통과 기준에는 없는 관찰).
- ⑦, ⑨는 "자료에 없습니다"라는 답 자체는 맞지만, 관계없는 조각 번호를 [ID]로 댔기 때문에 기준 1에서 틀림으로 판정했고, ⑧은 "자료에 없습니다"라고만 답하고 [ID]를 대지 않아서 맞음으로 판정했다.
- ⑩은 맞는 자료 QA-056을 2등으로 찾았는데, 답은 관계없는 QA-062(기초생활수급)를 댔다. 결론은 맞았지만 “400만원은 과세제외분으로 간주”라는, 자료에 없는 말을 넣었다. 경로우대 부분에는 번호가 없다.
- ⑪은 맞는 자료 QA-034, QA-083을 1·2등으로 찾았는데도 결론이 틀렸다. 20세가 넘은 장애인 형제자매를 다루는 자료를 거꾸로 읽어 “20세 이하 또는 60세 이상”이 필요하다고 했고, 관계없는 번호 5개를 함께 댔다. ②, ③처럼 자료는 맞게 찾았는데 답을 만드는 모델이 틀린 경우다.

## 과제 이후: 개인 앱을 위한 후속 개발 방향

2026-10-16 코드 검토를 바탕으로 정리한 설계 방향이다. 아래 내용은 새 구현의 성능을 검증한 결과가 아니다. 과제의 코드와 실험 기록은 보존하고, 후속 개발은 별도 개인 프로젝트에서 진행한다.

### 모두콘 참조 구현의 적합성

모두콘 실습 코드는 자료를 바꿔 RAG의 검색·답변 생성 흐름을 실험하는 출발점으로 적절했다. 다만 사용자의 조건을 받아 공제 여부 판단을 돕는 개인 앱에는 핵심 흐름을 다시 설계할 필요가 있다. 프롬프트만 계속 고치는 방식으로 해결할 수 있는지는 별도로 검증해야 한다.

현재 코드에서 확인한 한계는 다음과 같다.

- 검색은 벡터 상위 10개를 먼저 선택한 뒤, 중복을 제외한 BM25 결과로 나머지를 채운다. 두 검색 결과를 통합해 전체 순위를 다시 매기는 방식은 아니다.
- 관련성이 낮아도 가능한 한 15개를 채워 전달한다. 이 개수가 앱에 적절한지는 검증되지 않았다.
- 나이·소득·예외 조건의 해석과 비교를 답변 모델에 맡긴다. 실험에서도 필요한 자료를 찾고도 숫자 비교나 조건 해석을 틀리는 사례가 있었다.
- 화면에는 대화가 쌓이지만 모델에는 현재 질문만 전달하므로, 후속 질문에서 앞선 대화의 조건을 이어받지 못한다.
- 검색된 자료 전체를 출처 목록으로 표시하므로, 검색 후보와 실제 답변에 사용한 근거가 구분되지 않는다.

`id·text·url·section·vector` 조각 형식 자체가 부적절한 것은 아니다. 임베딩 모델과 768차원이라는 설정의 적합성도 숫자만으로 판단할 수 없으며, 실제 질문에서 필요한 근거를 찾는지 평가해야 한다.

### 재사용과 재설계

전체를 버리고 처음부터 작성하기보다, 기존 구현을 비교 기준으로 보존하면서 앱의 핵심 처리 부분을 새로 만드는 방향을 검토한다.

- 재사용 후보: 수집한 원문, 출처 연결, 검증된 모델 호출·스트리밍 코드.
- 재설계 대상: 질문의 필요 조건 확인 → 근거 검색 → 조건 비교 → 답변과 실제 사용 출처 표시.
- 역할 분리: 명확히 정의할 수 있는 조건 비교는 검증 가능한 코드로 처리하고, 모델은 질문 해석과 설명을 맡긴다. 판단에 필요한 정보가 부족하면 추가 질문한다. 조건과 예외의 정확성은 별도로 검증한다.
- 앱의 책임 범위 결정: 자료를 찾아 설명하는 기능인지, 사용자 조건에 따른 공제 가능 여부 판단까지 제공하는 기능인지 먼저 정한다.

### 검증 방법

새로 작성하는 것만으로 정확도가 개선되는 것은 아니다. 동일한 고정 질문으로 기존 방식과 새 방식을 비교하고, 검색이 필요한 근거를 찾았는지와 답변이 그 근거를 올바르게 사용했는지를 나누어 평가한다. 기존 11개 질문을 비교의 출발점으로 삼고, 후속 질문·정보 부족·경계 조건 사례를 추가한다.
